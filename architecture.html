DoubleSlash architecture

Identity lives on the device. Connections are negotiated between peers. Supernodes help move the bytes, without becoming the authority behind the conversation.

01 / Topology

Peers first. Infrastructure optional.

The native client owns identity, trusted peers, conversations, and room definitions. Direct and relayed sessions expose the same channel model: reliable streams, unidirectional streams, and datagrams.

No account service

A signed invite bootstraps trust. There is no first-party identity, discovery, or presence backend and no central feature registry.

One feature framework

Voice, chat, files, video, rooms, and games sit on capability negotiation. The desktop interface consumes the framework rather than bypassing it.

02 / Security model

Trust the peer. Limit the relay.

Ed25519 identities sign invites and signaling. The invite handshake binds its transcript and derives a session key with X25519 and HKDF. Post-handshake signaling checks signatures, timestamp freshness, and replay protection.

Visible to a supernode

  • Peer identities, room membership, and routing identifiers.
  • Connection timing, message types, signatures, and byte volumes.
  • Ephemeral room names and file-offer metadata, including file size and path.

Not available to a supernode

  • Decrypted room chat, voice, video, or shared-audio content.
  • Plaintext file chunks or room content keys.
  • A stored conversation archive or file cache for later delivery.

Privacy is not anonymity: routing metadata remains visible. Direct relay encryption uses a static pairwise key and does not provide forward secrecy. Room content fails closed when real group-key material is unavailable.

How room keys are distributed

The lexicographically smallest current member acts as the elected keyer. It seals epoch key material to each member and rotates the room key on departure. Receivers accept keys only from the elected keyer at a plausible epoch; acknowledgment and bounded retries cover lost distributions.

Where replay protection differs

Signed signaling uses a five-minute freshness window and a per-sender signature replay guard. Real-time room audio and receiver-idempotent ordered file payloads skip signature deduplication, but still require valid signatures and fresh timestamps.

03 / Session lifecycle

From an invite to a usable channel.

  1. Accept a signed inviteThe authenticated handshake establishes the peer relationship. The client persists trust locally; supernode identity is taken from the signed invite, not guessed from a relay URL.
  2. Exchange capabilitiesCAPABILITY_ANNOUNCE advertises supported features. Matching IDs and major versions define the negotiated intersection.
  3. Establish transportDirect sessions use an embedded quinn::Endpoint. A supernode relay uses identity-authenticated QUIC. Signaling prefers an established QUIC stream, with WebSocket fallback.
  4. Invoke an agreed featureFeature intersection, authentication tier, and required user consent are checked before dispatch. Inbound and outbound traffic is quota-controlled.

When direct calling stalls

After call acceptance, a five-second direct-connect deadline can trigger a temporary private SFU room on a mutually trusted connected supernode. Pending fallback is canceled if direct transport recovers or the call ends.

When a client restarts

Relay grants and supernode information prefer the live WebSocket, so an old QUIC queue cannot capture reconnect replies. Portal requests wait for relay readiness outside the manager event loop, with a bounded timeout.

04 / Capability layer

Features are contracts, not side channels.

conquerd-features is shared by clients and supernodes. Its registry owns descriptors, authentication tiers, consent, quotas, and channel framing. Optional features do not become mandatory services.

05 / Hosted experiences

Games are one consumer. Apps can use the same foundations.

A shared drawing surface and a multiplayer game have similar connectivity needs: load an interface, identify the participants, join a session, and exchange updates. DoubleSlash separates the hosted interface from the peer data path, so those building blocks can also support collaborative tools and node-specific portals without introducing a central account service.

Host the interface

web.host.app.v1 serves HTML, CSS, JavaScript, and assets from the supernode's web/ and games/ directories. The native client's embedded Chromium loads them through d://, using QUIC bidirectional request/response streams. This hosts an interface; it does not provide an application database.

Use the native bridge

window.conquerd.ready supplies the local peer identity, supernode identity, and portal APIs. The desktop client also exposes the same object as window.doubleslash, but window.conquerd remains the primary name for hosted pages to target. Channel open, send, poll, and close operations use the authenticated relay connection through /_conquerd/channel/*. Portal fetches reach the hosting node without a separate public HTTP endpoint.

Exchange session updates

The current ConquerdClient JavaScript SDK opens a named session and sends bytes through game.relay.v1. Cursor positions, drawing previews, and game-state updates can share this opaque datagram fan-out. The relay routes bytes; the application defines their meaning.

Add a distinct contract

A new cross-peer service belongs in an explicit x.<vendor>.* capability, with its own version, authentication tier, consent, and quotas. The Rust framework supports request, stream, and datagram features. Registering a module does not automatically expose it to JavaScript: a consumer and any required bridge integration must also be implemented.

An access portal, step by step

  1. Establish the invited relationshipThe native client authenticates to the supernode. Where its access policy requires a gate, the node can issue a portal-only relay grant rather than full service access.
  2. Load the gate on the restricted connectionThe page is reachable over web.host.app.v1 while room membership, relay datagram forwarding, and reliable relay signaling remain unavailable to the portal-only guest.
  3. Resolve access against the authenticated peer/api/access/status reports the caller's access state; /api/access/accept requests admission. The node binds these operations to the QUIC peer identity, not a page-supplied account name.
  4. Enter the permitted experienceOnce granted, the client can establish full relay access. Feature negotiation, consent where required, and room membership still apply; passing the portal gate does not bypass them.

What the framework supplies

  • Device-held identity and authenticated transport.
  • Hosted in-app interfaces and a native channel bridge.
  • Feature contracts, authorization gates, and traffic quotas.
  • Opaque relay forwarding without server-side gameplay logic.

What an app must still design

  • Its data format, validation, and participant permissions.
  • Loss handling: datagrams can be dropped or arrive out of order.
  • State recovery and late-join snapshots from participating peers.
  • End-to-end protection for private app payloads; opaque forwarding alone is not encryption.

Hosting is a separate trust boundary: the operator supplies the page's code and assets. An authenticated connection identifies the host; it does not make arbitrary hosted JavaScript trustworthy. The game SDK currently routes through game.relay.v1; passing another feature ID does not invoke a custom module. Native room chat, voice, and files stay in the desktop client, and a WASM plugin sandbox remains future work.

06 / Content paths

Different media. Deliberate delivery.

Voice

Opus audio travels over QUIC datagrams. Room voice can fall back to signed WebSocket messages. Room audio is end-to-end sealed; active-speaker forwarding uses packet arrival, not decoded sound.

Video

VP8 is available across platforms; Windows also supports Media Foundation H.264. Direct calls negotiate a codec. Room senders select a codec and stamp each frame. Room video has no WebSocket fallback.

Shared audio & synchronization

A session clock timestamps video and shared audio together. Audio-led playout holds or drops video to synchronize it; video without a current audio anchor free-runs. Shared audio follows the viewed video, independently of voice mute.

Files are offered, then pulled

Room file offers contain metadata, not an automatic upload. An accepting member requests chunks from the originator, which sends only to that recipient. Large transfers stream from disk without compression; the supernode stores no file copy.

The in-app portal is not this public website. Hosted pages load inside the native client through d:// and web.host.app.v1. Games use window.conquerd and the authenticated channel bridge, not a public browser transport.

07 / State & operations

Durable on clients. Ephemeral on relays.

Where state belongs
OwnerPersistent stateRuntime state
Native clientIdentity, trusted peers, local chat history, settings, encrypted room definitions.Sessions, negotiated capabilities, media pipelines, room keys.
SupernodeIts identity, peer trust, feature manifest, invite configuration, endpoint mailbox.SFU rooms, membership, routing, quotas, and cluster links. No content archive.

Clients rematerialize saved rooms on connection. Empty user-created rooms are collected after 15 minutes; the built-in default room remains. Removing a room from the sidebar is a local action, not server-side deletion.

Cluster replication

Members exchange room existence, client trust, Space roots, and opaque room chat/audio frames over authenticated cluster QUIC links. They do not replicate private-room per-peer ACLs. Space proofs, local invite tokens, and creator admission cover room access.

Cluster operations

The separate supernode manager provisions and deploys nodes over SSH. Cluster UDP ports are restricted to member IPs. Redeploy preserves the roster and cluster firewall rules; roster changes use an explicit cluster sync.

08 / Implementation

Three workspaces. Clear ownership.

conquerd-client

Separate desktop workspace. Qt / QML connects through CXX-Qt models and AppBridge to ConnectionManager, local stores, and media pipelines. Headless builds support tests.

rust/

The outer workspace contains the shared features registry, supernode, installer, and first-party Opus and VP8 wrappers. The installer handles release download, verification, and application.

conquerd-supernode-manager

Separate operations workspace. Inventory, SSH transport, provisioning, cluster configuration, and a CLI / terminal dashboard. It is not an identity backend.

The product is DoubleSlash and new invite and portal links are minted as d://, but identifiers that peers agree on are deliberately unchanged by the rename: crate names, the QUIC TLS server name, HKDF labels, the window.conquerd bridge, /_conquerd/channel/*, x.conquerd.* capability ids, and the legacy conquerd:// scheme, which is accepted on parse so existing invites keep working. Renaming any of those would split the network.

09 / Current state

Implemented does not mean finished everywhere.

IMPLEMENTED
  • Direct and relayed QUIC, capability negotiation, and encrypted room content.
  • Cross-platform VP8 and camera capture backends for Windows, Linux, and macOS.
  • Shared-audio synchronization and adaptive video bitrate.
  • Space Layer 1: authenticated room trees, proofs, and grants.
LIMITS & OPEN WORK
  • Screen/window capture and shared-audio capture remain Windows-only.
  • Non-Windows capture still needs real-hardware validation; the full two-client and room video checklist remains open.
  • Space Layer 2 cryptography and a WASM plugin sandbox are deferred.
  • Room key epochs are eight-bit; a simultaneous-join bootstrap race can require a later membership snapshot to recover.

Capture is a privacy boundary: whole-screen sharing includes pop-ups. On Windows versions below build 20348, per-application audio capture falls back to whole-machine audio rather than silence.
